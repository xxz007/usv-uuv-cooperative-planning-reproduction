# 04｜洋流、动态任务与故障接手

P4在同一执行器中接入时变洋流、新任务和任务能力故障。核心问题是：重规划必须从当前实际状态继续，同时正确处理已经完成的任务、健康艇服务进度、故障艇未完成任务和累计容量。

**同一场景只改变响应策略**

STATIC_FROZEN与DYNAMIC_REPLAN共享地图、初始Pyomo解、洋流、任务事件、速度和预算。前者保持原归属，后者响应已观测事件并接手剩余任务。

| 策略 | 完成任务 | 团队完成时间／s | 六艇全窗移动NEU |
|---|---:|---:|---:|
| STATIC_FROZEN | 16/22 | null | 212.864764 |
| DYNAMIC_REPLAN | 22/22 | 65 | 312.864764 |

这些是已保存统一案例的读数。本次学习笔记整理没有重跑该比较，完整来源见[P4结果入口](../../results/p4_dynamic/README.md)。

**事件发生时具体保留什么**

- t8起出现非零流；实际对地位移由水体相对运动与当前洋流共同决定，未到航点时保留该计划项。
- t11发布T21、T22，健康艇正在进行的服务保留进度和队首。重新规划从实际位置接入安全路径，不能通过取整把艇瞬移到栅格点。
- t24观察到U4任务能力故障，已经完成的任务不重复。故障中的未完成服务清零；接手艇需要重新完成规定服务。
- 累计接受不同任务ID占用容量；任务完成或转移不退还历史槽位。接手前检查实际已用加完整余路线预算。

规划器只得到已经发布的任务和当前观测状态，环境中的未来事件表不直接成为规划输入。当前响应是集中式、事件触发的，不直接等同于分布式协商或周期滚动优化。

**新运行示例**

按[复现说明](../../README.md#6运行指南)建立主环境和`.venv-solver`后，先生成初始解，再执行两策略：

```bash
.venv-solver/bin/python -B -m usv_uuc_cooperation.main solve --stage P4 --run-id learn_p4_initial_01
.venv/bin/python -B -m usv_uuc_cooperation.main run --stage P4 --case ALL --run-id learn_p4_pair_01 --initial-result "$PWD/results/p4_dynamic/runs/learn_p4_initial_01/初始分配.json"
```

两策略摘要：`$PWD/results/p4_dynamic/runs/learn_p4_pair_01/摘要.md`。关注完成数、团队时间和事件接手；原始数据再核对服务、容量与预算。

本例流场按时间分段、空间均一，等待／服务／故障驻留采用理想补偿。NEU仍按实际对地距离计算；没有据此完成水下六自由度、推进功耗或鲁棒控制研究。较低的失败组NEU与更高的动态组完成量应共同解读。
